# Pattern Audit — October 2026

The audit was done by pattern, not file by file. The decision log showed the same
kinds of bug being found one call site at a time (missing DB retry wrappers,
silently dying threads, drifted copies of a helper). Each section below is one
sweep: the checklist used, what turned up, and what was fixed.

Baseline at the start: in a clean checkout (CI, a cloud session, a new
contributor) **47 tests failed**, `ruff check src/` reported **63 errors**, and
dependencies **would not install on Python 3.12/3.13**. GitHub Actions has no
recorded CI runs for this repo, so none of this was visible.

---

## 1. Database transactions left open (write-lock leaks)

**Checklist:** for every write path, if an exception is raised *after* the
first write, is the transaction rolled back before the exception leaves the
function or is swallowed?

**Why it matters:** `get_connection()` caches one connection per thread for
the life of the process. An open write transaction on that connection holds
SQLite's single write lock until the same thread next commits or rolls back.
Every other writer (the other `--stream` stages, and the separate apply
process) waits out `busy_timeout` (30s) and fails with `database is locked`.

**Found and fixed (commit "Roll back open transactions on non-lock write failures"):**

| Where | What happened |
|---|---|
| `database.write_with_retry` | Rolled back only on `database is locked`. Any other exception (e.g. `transition_state`'s `ValueError("Job not found")`) re-raised with the transaction open. |
| Extension HTTP handlers in `launcher.py` (`add_job`, `jobs_mark`, `account_mutate`, `qa_create`, `qa_mutate`) | Broad `except` after writes, no rollback. The listener thread lives for the whole run. |
| `database.store_qa` | Swallowed failures, including a failed commit, leaving the INSERT pending. |
| `result_handlers._parse_account_lines` | Swallowed `store_account` failures mid-write. |

**Hypothesis to verify on the live machine:** decisions #183, #192 and #213
treated the lock exhaustion as raw contention ("a capacity ceiling no amount
of retrying can absorb"). A leaked transaction fits the evidence better: #213
saw a write wait out a **full 300 seconds** of retries, which contention from
short transactions shouldn't produce, but one stuck open transaction would.
After this fix ships, compare the count of
`DB write locked: giving up after 8 attempts` per hour of `--stream` against
the overnight logs from decisions #192/#209. If it drops sharply, close #183.
If it doesn't, the next step is `BEGIN IMMEDIATE` plus shorter transactions.

**Not changed (judged safe):** the per-item `try/except` loops that commit
once at the end (`acquire_job` sweeps, orchestrator startup re-queues). A
failed item there doesn't strand the transaction, because the trailing commit
still runs.

## 3. Drifted copies of the same helper

**Checklist:** same-named top-level functions in more than one module
(AST scan). For each, are the copies identical, and if not, is the
difference intentional?

**Found and fixed: discovery location filter** (commit "Consolidate four
drifted discovery location filters"). This was a real behavior bug, not just
duplication:

- jobspy, workday and smartextract read top-level `location_accept` /
  `location_reject_non_remote`. Neither `searches.example.yaml` nor
  `applypilot init` writes those keys. With them missing, **every non-remote
  job that had a location string was dropped**.
- greenhouse (also used by lever and ashby) read the documented
  `location.accept_patterns`, but **never applied any reject list**, and kept
  everything when the accept list was empty.

Now one module (`discovery/location_filter.py`) reads both key shapes and
treats an empty accept list as "no preference". The ATS crawls apply reject
patterns too.

**Worth checking on the live machine:** your real `searches.yaml` may hold
both key shapes. After this change, the reject patterns under
`location.reject_patterns` also apply to LinkedIn/Indeed and Workday, and
`location_reject_non_remote` also applies to Greenhouse/Lever/Ashby. Expect a
few more postings filtered at discovery, and check that nothing you want is
caught.

**Found, not changed (low value, logged in backlog as E5):** identical copies
of `_strip_html` (costco/amazon/greenhouse), `_get_ua`
(smartextract/enrichment), `_fetch_page` (costco/amazon); near-copies of
`_fetch_json` (5 modules), `_sender_domain` (tracking), and `load_employers`.

## 4. Trusting LLM output to be clean JSON

**Checklist:** every place model output goes through `json.loads`. Does it
handle code fences, prose around the JSON, and `<think>` blocks (all observed
live from qwen3)?

**Found and fixed (commit "One shared parser for JSON returned by LLMs"):**

| Where | Gap |
|---|---|
| `local_tailor.build_phrase_bank` | Bare `json.loads`. Any wrapped reply lost the whole generation round. Possible contributor to decision #133's "no survivors" entries. |
| `hackernews._parse_extracted_job` | Fences only. |
| `tailor.extract_json` | No `<think>` stripping. |
| `local_tailor._parse_plan` | `part.lstrip("json")` strips *characters* j/s/o/n, not the prefix. |

All of these now go through `applypilot/llm_json.parse_llm_json`. smartextract
keeps its own repairs and uses the shared parser as its last resort.

## 5. Clean-checkout health (tests, lint, CI, platform)

Fixed in the first commit of this pass:

| Problem | Fix |
|---|---|
| 35+ tests required the candidate's real `profile.json` / `resume.txt` | `conftest.py` supplies synthetic ones only when the real files are missing. Tests asserting real profile facts are marked `real_profile` and skip without one. |
| `scheduler._pid_alive` used only Windows APIs and returned False on Linux/macOS | The single-instance scheduler lock never blocked there. POSIX branch added. |
| `watchdog.py` hardcoded `C:\Users\phili\...` | Uses the repo root (the same directory on the original machine). |
| `psutil` not declared | Added to the `dev` extra. |
| ruff had no `select`, so newer ruff defaults added 60+ rules | Pinned to `E4, E7, E9, F, I`. Per-file E402 for two deliberate late imports. |
| CI matrix included 3.12/3.13 | python-jobspy 1.1.45–46 pins `numpy==1.24.2`, which doesn't build on 3.12+. Matrix limited to 3.11 (backlog item E1). |

Result: **2493 passed, 11 skipped** in a clean checkout; `ruff check src/`
clean.

## 6. Large files (not refactored in this pass, on purpose)

| File | Lines |
|---|---|
| `scoring/local_tailor.py` | 4,437 |
| `apply/launcher.py` | 3,341 |
| `database.py` | 3,064 |
| `cli.py` | 2,747 |
| `scoring/tailor.py` | 2,103 |

These weren't split in this pass. The test suite patches many names by
module path, e.g. `patch("applypilot.scoring.local_tailor.X")`. Once a
function moves to a new module, patching the old name with a re-export no
longer affects calls made *inside* the new module. Tests can keep passing
while no longer testing what they say they test.

The safe procedure is backlog item E4: move one cohesive group at a time,
update every `patch(...)` target that refers to it in the same commit, and
grep for the old path before merging. `database.py` is the best first
candidate. It splits cleanly into schema/migrations, state machine, retry
helpers, Q&A/accounts, and backfills.
