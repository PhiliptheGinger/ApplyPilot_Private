Scope: read-only. No source, test, config, DB, document, or repo state was modified. All DB access was via sqlite3 opened mode=ro (SELECT/PRAGMA only). Test runs were targeted subsets only (they use temp DBs; the full suite was not self-run per operating convention).

1. Executive summary
The architecture is genuinely good: a canonical state machine, a single canonical seniority predicate, bounded retries, a well-designed run-continuous scheduler, a thorough apply-safety prompt, and a deep anti-fabrication layer in tailoring. The decision log is unusually disciplined.

But the system is currently not doing what it is designed to do, for one dominant reason and several structural ones.

The single most important finding (P0): ~/.applypilot/resume.txt — the resume text fed verbatim into every scoring LLM call — is a fabricated placeholder:


PHILIP GINGER
Senior Software Engineer
Seattle, WA
SUMMARY  Senior software engineer focused on backend systems, automation, and AI-assisted workflows.
SKILLS   Python, TypeScript, SQL, APIs, Automation, LLM integrations, Testing, CI/CD
EXPERIENCE HIGHLIGHTS
- Built and operated end-to-end automation pipelines for job discovery and application workflows.
...
Wrong name, wrong state, a senior software engineer title, skills absent from profile.json, and ApplyPilot itself described as employment. scorer.run_scoring reads this file directly (RESUME_PATH.read_text()), bypassing resume_router, which every other stage correctly uses. Every scoring prompt therefore contains a direct internal contradiction: the system message (built truthfully from profile.json) says "this candidate has NO professional software engineering employment history… based in Mebane, NC", and the user message hands the model a senior Seattle backend engineer. The model believes the resume. Live score_reasoning proves it verbatim:

Anduril Deployment Lead: "The candidate's seniority and technical skills are a good match… The candidate is based in Seattle, WA." → 8
Twilio Software Engineer (L2) (the one job ever actually applied to): "The seniority level (Senior) and technical skills suggest a good fit… the candidate is based in Seattle, WA." → 8
Workday SDE – ML Ops (US Federal): "the role's security clearance and federal focus are compatible with their profile." → 8, applied, apply_failed
This single file explains the score distribution's shape, 116 Anduril defense jobs at ≥8, and both real application attempts.

Second-order failures compounding it:

The ready-to-apply queue is 100 % unapplyable. All 5 ready_to_apply rows are LinkedIn rows with application_url = ''; acquire_job requires application_url != ''. All 6,673 enriched LinkedIn rows have no application_url — yet nothing gates tailoring/cover on having one, so LLM spend goes to jobs that can never be submitted.
The ethical/defense exclusion is dead configuration. scorer._check_ineligible reads exclude_description_keywords; the live ~/.applypilot/searches.yaml (rewritten 2026-08-25) does not contain that key. The ~130-term military/weapons/surveillance list exists only in searches.example.yaml and in monkeypatched tests. Meanwhile Anduril (2,206), Raytheon (1,372), Boeing (614) and Axon (469) are among the largest employers in the corpus.
Discovery starves everything else. The last supervised run spent a full 2 hours on discover alone before the watchdog killed it, producing zero scored jobs, while 11,770 enriched, in-age, unscored jobs sit in the queue. run discover with no --source runs the JobSpy full crawl three times (jobspy, then linkedin, then indeed), 63 combos each, fully serial — against boards returning 403 on essentially every request.
Generated documents are defective. 271 of 326 (83 %) tailored .docx files contain the literal string Dates where employment dates belong — the tailoring prompt's own JSON schema example ("subtitle":"Tech | Dates") is being copied verbatim, and no validator inspects subtitle. Cover-letter .docx files collapse all paragraphs into one block.
The apply prompt instructs fabrication and states a falsehood. It renders "lives in Mebane, cannot relocate" (profile: willing_to_relocate: true), "This candidate is a   with   years experience" (empty profile fields), and "If the question asks 'Do you have experience with [tool]?' and it's in the same domain (DevOps, backend, ML, cloud, automation), answer YES." — on real submitted forms.
Working tree: the three modified files implement a narrow, well-documented IC-manager exemption (Account Manager / Customer Success Manager / Technical Account Manager / Sales Manager). It is correct, well-tested (277 targeted tests pass), and correctly closes the revalidate_seniority drift it would otherwise have created. Also untracked and not in .gitignore: watchdog.py and watchdog_logs/.

3. Known issues — status of each numbered policy area
3.1 Seniority — Working correctly, with one Policy ambiguity
eligibility.SENIORITY_TITLE_PATTERN + seniority_disqualifier is genuinely canonical: used by scorer._check_ineligible (pre-LLM), apply/launcher._auto_reject_title (pre-apply), tailor.classify_seniority_mismatch (pre-LLM), and eligibility.revalidate_seniority. L1/L2 and Engineer I/II are correctly allowed; L3+/Level 3+/SWE-SDE III+ are caught. 277 targeted tests pass.

Bare "manager": the uncommitted diff resolves the specific collision the brief asks about. _IC_CUSTOMER_FACING_MANAGER_TITLES exempts exactly Account Manager / Customer Success Manager / Technical Account Manager / Sales Manager only when every SENIORITY_TITLE_PATTERN match in the title is the bare token manager. Verified against live data: 121 rows unblocked, 1,941 manager-titled rows still blocked. "Senior Account Manager", "Director of Account Management", "Head of Customer Success", "Engineering/Product/Project/Program/Operations Manager", bare "Manager" all still disqualify. The implementation matches its documentation exactly.

Residual ambiguity (documented in-code, not a defect): title-only matching cannot see body-level people-management language; the module's own comment cites Brady Corp "Technical Account Manager" whose body opens "you will lead and manage a team". Severity: low — the LLM scorer does read the body.

Unwanted interaction (new): of the 121 unblocked titles, a large share are Axon law-enforcement/counter-drone roles ("Technical Account Manager - Counter-UAS / Drones", "Software Technical Account Manager - Cuyahoga County Sheriff's Office", "Customer Success Manager, Axon 911", "Regional Sales Manager | Federal Civilian"). Because the ethics filter is dead (§3.7), these now reach the scorer with no ethical gate at all. The exemption is correct; the ethics gap makes it consequential.

3.2 Security clearance — Working correctly (gate), Confirmed bug (no retroactive application)
Live measurement of the full corpus: 428 rows contain clearance language; 407 (95 %) are caught inside the 6,000-char scan head; 21 are only present beyond it. The two-tier design (bare TS/SCI disqualifying; Secret/Top-Secret requiring an explicit hard-requirement formulation) is sound, and I found no false positive in the corpus.

But the gate was added in 652cfb6 and never applied backwards. The exact regression case is still live:

Software Development Engineer - ML Ops (US Federal) · Workday · fit_score=8 · eligibility='eligible' · state='apply_failed'
reasoning: "the role's security clearance and federal focus are compatible with their profile"

_check_ineligible runs only inside score_job. No tailor-, cover-, or apply-stage clearance re-check exists (_auto_reject_title covers seniority only). revalidate_stale_scores cannot reach it (apply_failed ∉ _STALE_SCORE_REVALIDATABLE_STATES), and both revalidation functions are manual CLI commands wired into no automated path.

3.3 Sales / recruiting / adjacent roles — Working correctly
4b888af removed Sales Engineer / Solutions Engineer / Pre-Sales / CSE / Recruiter / Talent Acquisition-Scout-Sourcer / Account Manager / Account Executive from _INELIGIBLE_TITLE_PATTERNS, and the prompt gained a balanced rule (occupation is never the reason for a low or high score; quota/commission/1099 structure is). Live evidence it works end-to-end:

Full Desk Recruiter (Talent.com, Greensboro NC) → 8, "local residency in the Greensboro area… while they lack formal recruiting experience"
Sales Development Representative (Twilio, Remote-US) → 8, "aligns perfectly with their documented professional background in outreach, sales"
Notably these two are the only high scores whose reasoning is grounded in the real profile rather than the fake resume — because sales roles don't trigger the fake resume's engineering claims.

The live ~/.applypilot/searches.yaml exclude_titles does not contain "manager" (unlike searches.example.yaml), so the config layer does not defeat the exemption. The test test_config_exclude_titles_is_a_separate_mechanism_not_touched_by_this_change is a no-op on this machine — correctly guarded by an if.

4.7 reset_failed() resurrects archived jobs — Confirmed bug (P1)
launcher.py:2093-2127 force-transitions to ready_to_apply every row where apply_status is non-NULL and not applied/in_progress/needs_human — ignoring state entirely. Since acquire_job re-checks only seniority, applypilot apply --reset-failed would put the TS/SCI ML-Ops job (§3.2) back into a real submit path.

4.8 manual_only → manual_only audit-log hot loop — Confirmed bug (P2)
One Intel Workday job carries 408 transitions, of which 403 are manual_only → manual_only, reason acquire_job: manual ATS, written in 3 minutes. Two causes: (a) transition_state writes an audit row even for a no-op self-transition (and treats to_state == from_state as always legal even without force); (b) acquire_job recurses without depth bound on each manual-ATS / missing-URL skip (launcher.py:1828, 1848) — >1000 skips would raise RecursionError and kill the apply run.

4.9 Streaming mode cannot terminate — Confirmed bug (P2)
pipeline._PENDING_SQL disagrees with get_jobs_by_stage. Measured live:

stage	_count_pending	actually selectable
score	14,558	11,770
tailor	4	2
cover	40	1
_run_stage_streaming breaks only when pending == 0. The 2,981 archived-but-unscored rows can never be drained, so pending never reaches 0 and the score/cover threads loop indefinitely. The progress heuristic is also dead: _run_score/_run_tailor return {"status","job_ids"} and _run_cover returns {"status":"ok"} — none of the counted keys — so progress == 0 always fires the 10 s back-off branch.

4.10 transition_state docstring contradicts implementation — Confirmed behavioral inconsistency (P2)
database.py:544: "Uses BEGIN IMMEDIATE so concurrent writers don't race on the state column." The function issues no BEGIN. It does SELECT state then UPDATE — a plain read-then-write TOCTOU. Under --workers > 1 two threads can both read the same from_state and both write.

4.11 Stale applying row with no recovery path — Confirmed bug (P2)
Software Engineer - AI Trainer (SimplyHired) has state='applying' since 2026-08-21 with apply_status = NULL. The stale-lock sweep keys on apply_status = 'in_progress', so a row whose apply_status was cleared but whose state is applying is stuck permanently — applying is not selectable by acquire_job and nothing else resets it.

4.12 Migration transitions re-emitted repeatedly — Confirmed bug (P3)
The same Intel job has 10 NULL → enriched "migrated 2026-04-24" rows spanning 2026-08-17 to 2026-08-20. The migration audit write is not idempotent, polluting the trail.

4.13 Score instability across runs — Plausible concern requiring further evidence
The same Intel job scored 8/10 on 2026-08-19 and 7/10 on 2026-08-21 — crossing the min_score = 8 boundary. Re-scoring is not idempotent and there is no confidence band or tie-break; a job's fate can flip on identical inputs. Only one clean instance observed.

4.14 Unbounded disk growth — Confirmed bug (P2)
~/.applypilot/dashboard.html = 111 MB. view.generate_dashboard (view.py:420) selects ALL jobs with no LIMIT and embeds each full_description twice (300-char preview + full HTML).

4.15 Permanent disqualifiers are treated as retryable — Confirmed behavioral inconsistency (P3)
_mark_tailor_result routes seniority_mismatch, no_supported_evidence, and local_realization_failed to tailor_failed, which pending_tailor re-selects up to 5 times. seniority_mismatch is deterministic and permanent — it burns 5 selections and 5 audit rows per job to reach the same answer.

4.16 pending_apply is a dead, misleading query — Confirmed behavioral inconsistency (P3)
get_jobs_by_stage("pending_apply") has no state filter and no min_score; it currently returns 286 archived rows with tailored resumes (fit_score as low as 1). The real apply path uses acquire_job and is safe, but any future caller of this stage name inherits a full eligibility bypass.

4.17 applypilot status over-reports — Confirmed behavioral inconsistency (P3)
get_stats uses the same unfiltered counts: tailored = 321 (308 archived), unscored = 14,558 (11,770 actionable). The funnel display does not reflect what any stage will actually process.

4.18 Duplicate postings consume the pipeline — Plausible concern
2,175 duplicate groups by (title, company/site) covering 8,425 redundant rows; 32 groups share an identical application_url (165 extras). company is NULL for all LinkedIn rows, weakening both the per-company cap and the duplicate guard. The 4 seasonal NC postings each consumed a full tailor + cover + PDF cycle. acquire_job's NOT EXISTS guard does prevent duplicate submissions once one variant is in flight — that part works.

4.19 run_continuous dies on any unhandled run_once exception — Confirmed bug (P2)
scheduler.py's while True: has no per-cycle try/except; only KeyboardInterrupt is handled, and the generic except Exception: re-raises. A single transient DB lock or throughput-query failure terminates the whole loop.

9. Discovery / enrichment problems
Discovery — the primary structural problem.

_run_discover with sources=None runs jobspy (all boards) + linkedin-only + indeed-only — the same 63-combination matrix three times. Fully serial (_full_crawl's for completed, s in enumerate(searches)), max_retries=2 with 5 s/10 s back-off per failure.
No --limit, no time budget, no per-source cap. run --limit is documented as "Max jobs per stage (score/tailor/cover)" and never reaches discover.
Three of four boards are hard-blocked. From the 2026-08-26 run's stderr: Indeed 403 (every request), ZipRecruiter 403 (every request), Glassdoor 400/403, plus a GlassdoorException traceback and a LinkedIn Invalid country string: 'bulgaria' parse error ending in "all sites failed". searches.yaml still lists zip_recruiter (the code's own default comment says it was removed 2026-06-10 as Cloudflare-blocked) and google (unsupported by the pinned jobspy — a warning on every run).
Measured cost: 2 hours, killed at the limit, 0 jobs scored.

13. Continuous-operation problems
The right unit of work already exists. scheduler.run_once is well-designed: bounded score batch (min(max_batch=20, pending)), throttled discovery (1 h), need-driven tailor/cover (plan_upstream_work — need wins when smallest), throughput-measured capacity, Claude-availability gating, single-instance PID lock with liveness check, injectable dependencies. No crash/restart loop exists — watchdog.py never restarts. That's safe, but it also means an early crash silently ends supervision.
Verdict: the machinery can do the required cycle. The smallest architectural change is to make the discover stage bounded (source subset + per-run cap or deadline) so it stops monopolizing the cycle, and to point supervision at run-continuous.

Aspect	Finding
Placement	Reasonable but unmanaged. Repo root is fine for a per-machine supervisor, but it is untracked and unignored — one git add -A commits hardcoded C:\Users\phili\... paths and run logs. Decide: track it under scripts/ with paths from env/argv, or add both to .gitignore.

Output capture	Missing. No stdout/stderr on Popen; ApplyPilot's output goes to the watchdog's own console and is lost when detached. The deleted version had this.
Time limit	Missing. No cap; the 2 h bound in the logs came from the lost version. Without it a wedged run is supervised forever.
Trigger design	Sound in shape, likely inert in practice. Requires PercentDiskTime ≥ 99 and AvgDiskSecPerTransfer × 1000 ≥ 1000 ms for 10 consecutive 2 s samples. Every sample in the retained log shows latency=0.0 ms (peaks: 44 % active, 0.84 MB/s). The AND is conservative — it will not false-trigger, but on this hardware it will also probably never fire, so the real 2 h/2 GB-log/111 MB-dashboard problems go unaddressed.
Monitoring cost	Notable. Spawns a full powershell.exe -NoProfile + Get-CimInstance every 2 seconds — a process launch every 2 s for the entire run. On a machine already under disk pressure this is itself a contributor. A single long-lived PowerShell reading in a loop, or psutil.disk_io_counters() (psutil is already a dependency), would be far cheaper.
Process-tree handling	Good for a plain-subprocess design. psutil children(recursive=True), terminate-then-wait_procs(timeout=5)-then-kill.
Orphan risk	Real, Windows-specific. No Job Object / CREATE_NEW_PROCESS_GROUP. children(recursive=True) is a snapshot: grandchildren spawned during the 5 s wait, or already-reparented processes, escape. ApplyPilot's Tier-3 path spawns claude → Playwright → Chrome trees; taskkill /T /F or a Win32 Job Object with KILL_ON_JOB_CLOSE is the robust answer.
Signal handling	POSIX assumption. psutil.terminate() on Windows is TerminateProcess — no graceful shutdown, no chance for ApplyPilot's finally: blocks (scheduler lock release, WAL checkpoint, log teardown) to run. Combined with a 245 MB WAL-mode DB this risks leaving -shm/-wal and a stale scheduler.pid.
Watchdog exits if it can't monitor	Race: the loop condition is while applypilot.poll() is None, but the sleep and PowerShell call happen inside. If ApplyPilot exits during the ~2-10 s PowerShell window, one more sample is taken against a dead process — harmless, but it also means the exit is detected up to 12 s late.
Exception handling	except Exception: log(...) inside the loop and continue on stats is None — resilient, but a permanently-broken counter (a common Windows condition; lodctr /R is sometimes needed) degrades silently to "no supervision" with only a WARNING line.
Restart / crash loop	None — it never restarts. Safe from restart storms, but an early ApplyPilot crash silently ends supervision with no alert.
Log growth	Watchdog's own log: one line per 2 s ≈ 43,200 lines/day ≈ 3-4 MB/day, appended with an open()/write()/close() per line — 43k file opens/day on the disk it is monitoring. A new file per run, never pruned. Supervised logs: the lost version's _err.log reached 62 KB in 2 h, dominated by repeating 403s.
Sleep-on-trigger	Blunt. Suspending the machine stops a pipeline problem by stopping the computer. Reasonable as a last-resort hardware guard; it should not be the only response, and it should not fire without first attempting a graceful stop (applypilot stop --stream / the run-state/stop-stream flag both exist and are unused here).
Should it stay external? Yes — with a small integration boundary. External supervision is the right shape for a hardware-safety guard: it must survive the thing it supervises. But it currently duplicates capability ApplyPilot already has and ignores the graceful paths ApplyPilot already exposes. The minimal boundary:

Supervise run-continuous, not run discover.
On trigger, first write ~/.applypilot/run-state/stop-stream (or send the documented stop) and wait; escalate to tree-kill only if that fails; treat sleep as a final, separate hardware guard.
Kill via a Win32 Job Object or taskkill /PID <pid> /T /F so Chrome/Claude grandchildren cannot orphan.
Restore output/err/meta capture and the wall-clock cap from the lost version; add a hard byte cap or rotation on the captured stderr.
Sample with psutil.disk_io_counters() instead of spawning PowerShell every 2 s; log a summary line per minute rather than per sample.
Move it to scripts/watchdog.py with PROJECT_DIR/LOG_DIR from env or argv, and either track it or add watchdog.py + watchdog_logs/ to .gitignore.
20. Proposed next experiments (small real-data batches)
Experiment 1 — Quantify the fabricated-resume effect (highest value, cheapest).
Take 30 already-scored rows stratified across the bands (10 defense/Anduril at 8, 10 SWE-II/L2 at 8, 10 IT-support/NC at 8-9). Re-score them twice: once with the current resume.txt, once with resume_router's profile-derived reference. Same model, same temperature. Success: the Anduril/Raytheon/Boeing/Axon block is cleanly separated with <1 % collateral on IT-support/NC roles (watch "dod" as a bare substring and "national security" inside boilerplate). Success: discover < 20 % of cycle time, ≥20 jobs scored, no exception terminates the loop. This directly tests §13.
