**Addendum, same day: real prior art found for the blocking-vs-skip question, per explicit user request ("scope this problem out. Maybe someone out there's solved it").** Confirmed via web search, not guessed -- this exact problem shape is well-established and solved in two adjacent industries. (1) **Cloudflare's "Browser Run" HITL handoff** (shipped 2026-07-28, a real, current product feature): an agent signals it needs help, a human steps in through a noVNC-based "Live View" to handle the stuck step directly in the live browser, and the agent resumes automatically once the human is done -- the session's cookies/login state survive the handoff intact ("a quick re-open lands you back where the human left off"), which is exactly the concern that's been blocking a skip-and-continue redesign here (losing an already-completed Lumen-style 2FA login, decision #196). (2) **UiPath's Action Center** (a mature, decades-refined RPA pattern): `WaitForQueueItemAndResume`/`WaitForAppTaskAndResume`-style activities SUSPEND a workflow into a durable, independent queue item the moment human input is needed, rather than holding a bot/worker resource idle the whole time -- the suspended task is a first-class object that gets picked up and resolved on its own schedule, and resumption does not require the SAME bot that originally suspended it. Both real systems converge on the same core architectural move ApplyPilot hasn't made yet: **decouple the browser SESSION's lifecycle from the WORKER THREAD's lifecycle.** Today's `--workers N` ties worker_id 1:1 to both a CDP port and a persistent Chrome profile directory (`chrome.py`, decision #32) -- that 1:1 binding is the actual structural reason a `needs_human` pause currently has to block its own worker rather than just releasing it. This is the same underlying fix Future Work item 36 (persistent per-worker Playwright MCP server) and item 46 (cooks/servers split) were both independently reaching for -- all three turn out to be the same root architectural gap (worker identity and browser-session identity are currently the same thing when they don't need to be), not three separate problems. Real open implementation questions still unresolved: how the MCP-side connection (Claude Code's `--mcp-config`, spawned fresh per job today) would need to change to support a worker attaching to an ALREADY-RUNNING Chrome+MCP pairing rather than always spawning its own (the exact gap item 36 already flagged as needing a persistent/HTTP-mode Playwright MCP server, not yet confirmed to exist); and what the pool's own failure-recovery story looks like if a checked-in session goes stale/crashes while no worker holds it. Not started -- this addendum exists so the next session scoping this has real prior art and a concrete direction to start from, instead of re-deriving it from zero.
